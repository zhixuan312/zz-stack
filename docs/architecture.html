zz-stack Platform architecture A solution development life cycle, running

A solution development life cycle that actually runs — agents do the work, people make the decisions, and every step leaves the evidence that makes the next one better.

What it is

A platform that a delivery method runs on, rather than a document describing one. It stitches the parts together — the method, the third-party systems, the people, the records — into something that executes, refuses, and remembers.

What it is for

Delivering software reliably enough to be defensible: every decision has a name against it, every claim has evidence behind it, and the way we work improves because using it produces the data that shows where it does not.

The bracket on the right is the whole argument. Work produces evidence as a by-product of being done — not as a reporting exercise — and that evidence is what tells us which layer to change next, and whether the change helped.

Who reaches this, and through what

The method
Skills, the team's store, documents and their gates, and where each initiative stands.
Your own keys
A person's own credentials for each third-party system, and their platform token.
Administration
People, teams, tokens, which method a team installed. Every tool authorises per call.
Building blocks
A third-party system, reached through one door so the call is recorded and scoped.

Many clients, one method. A chat interface, a terminal, a browser — each receives the same method projected into its own shape, so the way work is done does not change with the tool used to do it.

The spine

How work moves

The platform does not impose one way of working. It imposes a shape — and a method fills that shape in with its own stages, its own documents, and its own decision points.

First, the shape

Everything below is true of every method that runs here. None of it says how many stages there are or what they are called.

A lifecycle written in a document is a wish — it works only while everyone chooses to follow it. A platform that will not close an initiative whose approval carries no name is a mechanism.

How it gets better

Learning & Evaluation

Three published mechanisms, each solving a different part of the problem — and the measurement discipline none of them specifies, which is the part we had to build ourselves.

Improving a system whose components are written instructions is a young field with real prior art. We did not invent a loop; we assembled one — and the three below are not three versions of the same idea. Two of them are method: Warp gives the shape of the loop and who signs off; GEPA gives the way to reflect and what “better” is allowed to mean. The third is engineering: Hermes is where we look to see how any of this survives contact with running code — how a proposed change physically lands in a file, what a skill looks like on disk once it has grown beyond prose, and how the thing keeps evolving with nobody watching it. Theory says a change should be made; Hermes shows what making it costs.

What changes the base skill, as a plain file the system's textual parameters SKILL.md, and beside it scripts/, references/, assets/
How a change is accepted a human reviews and merges it, through ordinary code review kept if it improves; candidates that win on different cases are all kept rather than one winner autonomously — or staged for human approval when configured to
What it gives us the shape — two skills, one doing the work and one improving it, and a change that a person signs off the method — reflection in sentences rather than a score, results kept per case, one change at a time the engineering — how a change actually lands: patch in preference to rewrite, writes staged for approval rather than applied, and a skill as a directory (scripts/, references/, assets/) rather than a page of prose

What none of the three specifies

The measurement discipline — the part we had to build
A control that tests the judge
Every score is produced twice: once against the real requirement, once against a neighbour's. If the second scores as highly as the first, the reviewer is rewarding confident writing rather than reading, and that day's numbers are discarded rather than explained.
A measured floor, and a third verdict
How much a score moves between two runs when nothing changed, measured by repeating identical work. A claimed gain smaller than that spread is reported untested — not “slightly better”.
Generic before it earns an edit
Strip out every noun belonging to the subject matter. If the fault still describes something, it is the method's habit; if it disappears, it belonged to that one delivery. Only the first kind may change a skill, because a rule written for a one-off is read on every run forever.
A definition of good that we did not write
The rubric is derived from the step's own output. Writing it ourselves would be setting the exam we are sitting.
The expectation comes first
What a good answer would contain is written from the requirement alone, by a reader who never sees the produced document. That blindness is the only reason the comparison means anything.

A document can carry every fact, hold every required section, and still be the wrong answer — so form and quality are measured with different instruments, and the two are never added together.

One measurement, end to end

This is a run against the first stage of ops-flow, the step that turns a stakeholder's brain dump into a stated need. Thirty pieces of work from twenty-seven different teams.

  1. CollectThirty deliveries, each a different team's request. The corpus is work the method was asked to do.
  2. Define good, without writing it ourselvesA model reads the step's own instructions and three of its real documents, and states what separates a strong one from a weak one. Five dimensions come back. Every one needs a reader; anything a script could check is rejected.
  3. Score, with the evidence attachedEach document is marked against those five dimensions, and every score must quote the document. 3.42 of 5 overall.
  4. Test the judge, not the workAll thirty are scored again against a neighbour's requirement. The result collapses to 1.00, and 104 of 104 are caught as answering a different problem. The control is a real document, not a scrambled one — a harder test to pass. The reviewer is reading.
  5. Find what recursAn expectation written blind from each request is compared to what was produced. One fault appears in 13 of 30 — in organisations sharing no vocabulary: an ambiguity in the request is quietly settled and written down as though it had been stated.
  6. Propose exactly one changeA passage is drafted for the step's instructions, quoting the fault that earned it. The step already contained a rule against this. The defect was not a missing rule but one pitched too abstractly to survive a real brain dump.
  7. Measure it, and refuse to claim itRun on eight deliveries the change was not derived from. The floor is 0.436, so at that sample nothing under 0.31 can be distinguished from noise. Measured delta: 0.000. Verdict: untested — and the change was reverted.

The weakest dimension is the entire point of the exercise: it says where the next change belongs, and nowhere else. Ending on a reverted change is not a failure of the loop — it is the loop working. A mechanism that never returns “untested” is one that will report noise as progress.

What it remembers

Knowledge

Two different things are worth keeping: the record of what happened, and the lesson drawn from it. They have different owners and different lifetimes.

The lesson belongs to the team, not to the delivery that produced it. A record is closed when the work is; a lesson keeps working long after.

What a team's knowledge base actually looks like

This is our own team's store, on disk, today. Every team gets the same shape — including us, which is the point: the platform team is a tenant of its own platform, with no separate mechanism.

One method names eight required components. Another heads its list "EXACTLY these
sections". A third specifies a heading and adds, in those words, "so a reader and a
check can both find it". Grepping the whole repository for any of those names returned
nothing: no code knew they existed, and the audit meant to catch a missing one was
another model reading the same document.

A heading list is the cheapest kind of fact — present or absent, no judgement. Whenever
a method states a rule of that kind, the platform should be the one holding it, with the
method declaring WHICH in its own manifest. The rule stays the method's; only the
enforcement moves.

Why: a check a model performs is the tier this platform agreed to use last, not
first, and it is the tier that fails silently.
How to apply: when a skill says "must contain", ask what would grep for it. If
nothing does, that instruction is advisory no matter how it is worded.
See [[an-instruction-that-produces-no-artifact-will-be-skipped]].
A lesson that cannot be traced to the work that produced it is folklore. Evidence is a required field, and the How to apply line is what makes it reusable rather than merely true.

Why it can be trusted

Governance

A document produced here should be defensible to someone who was not in the room — which means the machine, not the author, decides what counts as approved.

Approving should be an action taken, not a sentence written. The moment a signature is something an author can type, it stops being evidence and becomes a formatting convention.

One real document's envelope

The top of a specification. The example is invented; the SHAPE is not. Everything here is written by the platform — the author writes the prose below it and cannot type any of this.

This document is on its fourth version, and each revision says why. The three earlier ones are still there, frozen under _versions/ at the moment each was approved — the folder visible in the store on the Knowledge tab. Two stakeholder decisions are attached as sources — not summarised, attached — and the chain back to the intent it answers is a field, not a convention. A reader who was not in the room can reconstruct the whole argument from this header alone.

Somebody else's capability

Building blocks

Third-party systems do the specialised work. The platform's job is to make them reachable, scoped, recorded and comparable — without growing a service for each one.

A call that succeeds can still cost two hundred thousand words of working memory. Counting failures cannot see that, so cost is measured as its own signal.

One block, measured

A case-management system of the kind this platform integrates with. Every number here is read from the platform's own record of calls it has already made — nothing was instrumented to produce them.

What its calls cost us
  read_api_spec        803,840 bytes average   peak 1,229,671   over 32 calls
  read_user_guide      436,790 bytes every single time      over 23 calls
  — neither is a failure. Both SUCCEED, so no error is ever recorded, and
     the only symptom is a caller whose working memory is gone

What it says when it refuses
  27 refusals across a day of work, of the form:
      "Request failed with status code 422"
  — no field, no value, no reason. A caller cannot learn from that, and
     neither can any guidance we write beside it

What that means for us
  Normal advice — "read the spec before guessing at arguments" — costs about
  200,000 words of context here. So the guidance we wrote says the opposite:
  use the tool descriptions already in front of you, and never call that tool.
This is why cost is measured as its own signal. Counting refusals gave this block a clean score while it was consuming entire contexts — and the one genuinely useful instruction we could write for it is the reverse of what we would write for a well-behaved system.

Who is acting

Identity & Access

Authorisation is answered on every call, never cached into a client. And the answer has to stay true at the boundary with someone else's system.

Delegated access is not a better credential. It changes who is acting — which is the only way an external audit log can name the person instead of naming us.

One person, one call, traced through

What actually happens when a person asks an agent to look at a case — and what the third-party system records at the far end of it.

Specimen · a single call, end to endthe credential is theirs, not ours
1 · they are identified
    the platform resolves the person to one record — email is the key, and it is
    case-insensitive at every hop, so a login that capitalises differently still
    finds the same person

2 · their own key is attached
    the credential store is keyed by person, then by system:

        { "<person@team>": { "casebox": "…", "RuleMill": "…", "bookit": "…" } }

    three systems, three separate credentials, all belonging to that one person.
    Nobody inherits anybody else's.

3 · the block sees a principal, and applies its limits
        role   : api_key
        name   : <the person's key>
        apps   : [ one app ]         quota: 20 users
        get_apps → 403   — listing every app is above what this principal may do,
                          and the block is right to refuse it

4 · the call is recorded
    which person, which method, which step, which system, whether it worked,
    and the reason if it did not
Step 3 is the part worth dwelling on. That 403 is not a bug to be worked around — it is the third-party system correctly enforcing a boundary on a credential that belongs to one person with access to one app. If the platform used a single shared key instead, that boundary would silently disappear and every person would inherit whatever the shared key could reach.

Where it runs

Operations & Portability

The same platform has to run in places with different rules about what may be used. That is a design constraint, not a deployment detail.

Changing a supplier should be a configuration change, not a migration. That only holds if the capability was named before the supplier was chosen.

The same platform, two environments

What is actually different between where this runs today and where a stricter deployment would run it — and, more importantly, what is not.

  the method                           nothing — the stages, the gates, the

What it would cost without ports
  every capability wired straight to one supplier, so changing any of them is a
  migration with its own project plan rather than a value in a file
A team's history being a git repository they own is the sharpest case: it means a team leaving takes their documents and the authorship of every change, readable with nothing of ours installed. Portability stops being a promise in a document and becomes a property of where the data already sits.
