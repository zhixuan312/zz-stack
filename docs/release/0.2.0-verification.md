# 0.2.0 — what was verified, and how

Status: VERIFICATION RECORD (2026-08-26). Rewritten as the release was cut — the gate count,
the multi-team work, and the scenario result below all moved after the first draft.

The date on this line is the stamp; the 2026-08-25 further down is when the host was built,
which is a fact and not a status. They were the same line once, so "is this current?" and
"when was it installed?" had one answer between them.

The stamp stays at 2026-08-26 through every release since, ON PURPOSE. Two tool names below
were retargeted when the Python was removed — the tools still exist and still do what this
says, under `npm run` — and that is an edit to keep present-tense sentences true, not a
re-verification. (This sentence named a specific version until 0.4.1, which made the one line
arguing that a record's date must not move into a line that had to be edited every release —
and it had already gone stale once.)
Moving the stamp would claim 0.2.0 was checked again on a later host, and nothing here was
re-run. A record's date is when the running happened; only a live document's date is when
somebody last confirmed it.

Every claim below was produced by running the thing, on `zz-stack-debug`
(203.0.113.11), a host that began as bare Ubuntu with no Docker. Nothing here is
inferred from reading code. Where something was NOT verified, it says so.

## The deployment

Built from scratch on 2026-08-25: Docker installed, images built from source, Caddy
issuing certificates for `152-42-253-115.nip.io` and `api.152-42-253-115.nip.io`.

Seven containers: `librechat`, `mongodb`, `zz-core`, `cred-proxy`, `n8n`, `bookit`,
`postgres`. **No Open WebUI. No Redis.**

**The database carries no trace of the old front end.** Verified directly:

```
 table_schema | tables
--------------+--------
 zz           |     10
```

One schema, ten tables. Zero `public` tables — where Open WebUI's 43 lived on the old
host. The swap moves no platform data because the front end never owned any.

## Identity, end to end

A person's own token, from the browser, resolved by the gateway, answered by zz-core:

```
get_my_info → {"email":"sam@example.com","role":"admin","team":"product_group_1"}
get_my_info → {"email":"test_user_1@example.com","role":"user","team":"product_group_1"}
get_my_info → {"email":"test_user_2@example.com","role":"user","team":"product_group_1"}
```

Each is a real tool call made through the browser agent, not a database read. No change
to `identity.ts` was required: the PAT path already existed for Claude Code and Codex, and
the browser now uses the same one.

**All three members are provisioned and working** — account, platform token stored against
every MCP server, agent created from the registry, 139 tools each.

## The bootstrap, which had no door

A fresh Open WebUI-free install could authenticate nobody: `issue_pat` and
`issue_my_access_token` both resolve the caller before minting, and the only identity a
browser ever carried came from the old front end's forwarded headers.

`deploy/issue-first-pat.sh` was run on the new host and the token it printed authenticated
against `/core/mcp` — HTTP 200. That is the whole reason a fresh install is possible.

`BOOTSTRAP_TEAM` was verified the hard way: the first boot produced a superadmin and **no
team**, because the variable was in `.env` and never passed to the container. A deployment
in that state looks healthy and writes every document into a per-user store. Fixed, then
confirmed: `platform db seeded: superadmin sam@example.com, team product_group_1`.

## Context, measured rather than assumed

A live run reported **115.1K of 115.5K used, 91.1K of it MCP tool schemas, 403 tokens
free** — and separately hit `Recursion limit of 120 reached without hitting a stop
condition` while building.

| | before | after |
|---|---:|---:|
| Context window | 115.5K (LibreChat's guess) | **1,048,576** (`deepseek4.context_length`, from the provider) |
| Tools on the agent | 237 | **139** |
| Tool schemas | 91.1K | ~53K |
| Share of window | **79%** | **~5%** |
| Agent-loop budget | 120, reached | **400** (ceiling 600) |

The per-tool cost is ~380 tokens, measured (91.1K ÷ 237). That number is what makes the
scaling question answerable: an agent carrying 100 blocks at ~25 tools each would spend
~950K tokens on schemas alone, which is why the registry — not the deployment — decides
what an agent carries.

## Backups

`deploy/backup.sh` was run on the new host and produced: platform database 27KB, artifacts
13KB (17 entries read back and matched), credentials (1 entry matched), **LibreChat's
MongoDB 431KB**, verified by `mongorestore --archive --gzip --dryRun` rather than by
measuring the file.

Two defects were fixed to get there: the script hard-coded a `zz-` container prefix, which
is the compose project and differs per host — on this one it would have run green while
backing up nothing — and LibreChat's database was not covered at all, against upstream that
ships no backup guidance whatsoever.

## The gate

**64 checks passing.** Eight were failing after the removal, every one a place the old
front end was still assumed; five of those were checks that read `bootstrap_webui.py` to
learn what the browser offered.

Twelve are new since, and every one was verified the same way — by breaking the condition it
guards and confirming the check names the fault. Each exists because something actually
failed: four front-end settings the deployment does not work without; a block dying
mid-stream taking the gateway with it; an unknown MCP session answered `400` instead of
`404`; a compose file naming a Dockerfile that is not in the repo; a `--dry-run` that wrote
git history; a scenario able to pass on the conversation rather than the record; and the team
a person acts for being asserted by a client rather than stored.

Two of those break-tests failed to bite on the first attempt and were rewritten — a `sed`
that silently did not apply, and a guard anchored on the wrong line. A check proven by a
break-test that did not actually break anything is not proven.

## Defects the suite found in itself

Both were reported as flow failures, which is the expensive kind of wrong: the thing that
looked broken was working, and the thing doing the looking was not.

**The harness could not tell a finished flow from an unfinished one.** S1 completed, and the
agent closed it — "this initiative is closed with `outcome: accepted`. There is no open gate,
no pending decision, and no truthful place to record another 'approved.' I won't fabricate
one." `classify()` had no rule for the flow's terminal state, read it as a gate, and answered
"approved" five times. The scenario was reported as hitting max turns on a flow that had
already succeeded. `npm run classify-cases` now keeps those exact replies as cases, with
negative controls, and the gate runs it.

**The suite could not be run twice in one day.** `RUN_TAG` was the date, so a second run
shared the first's namespace and found its finished work. The agent read the record and
declined to duplicate it — correctly — and the harness spent its whole turn budget asking an
agent with nothing to do for approvals it would not fabricate. The tag is unique per run now.

Neither defect is about the front end. Both were invisible for as long as the suite was run
once, on a store nobody had run it against before.

Running it repeatedly found more of the same kind, and they are worth naming because every one
made a working platform look broken:

- **A scenario could pass on the conversation alone.** A round reported four passes against
  three closes in the ledger. Acceptance now requires a ledger row — appended by zz-core,
  unwritable by the model — and compares the closed initiative NAMES, because a count is also
  satisfied by finishing work another scenario abandoned, which is exactly what S3 did to S1's.
- **The harness answered "approved" to an agent that had just said there was no gate.** S1
  spent 26 turns on that, three rounds running; S2 and S5 later spent their whole budgets the
  same way. The stakeholder's real answer already existed in the scenarios and was never
  reached, because the routing rule listed the phrasings of the day.
- **A provider rate limit was reported as a flow failure.** Three scenarios were called
  regressions before anyone read the front end's log. Preflight now asks whether the model
  answers at all before spending a round, and a blocked run exits 2 rather than 1.

`npm run chain-check` exists because of this pattern: it walks the document chain over MCP
with no model in the loop, so when a provider outage means the harness cannot get a turn, the
question "does the PLATFORM still work" still has an answer. It reports 12/12 here.

## A person in two teams — built, and the two designs it took

An agent used to be provisioned per (team, flow) and labelled "Solution Agent — ops-flow for
product_group_1". With one team that is accurate. With two it was not, and the platform picked
the active team by role and then alphabetically — a choice nobody made and nobody could see.

**Settled: a PAT is a person, not a team.** One person holds one token and belongs to as many
teams as they belong to. A credential that carries a team makes identity mean two things and
hands people a keyring for a fact the platform already knows.

The first build made the AGENT carry the team: one agent per team, each pointing at its own
`zz-core@<team>` entry in the front end's config, sending a validated `x-zz-team` header. It
worked — verified with one token and two teams, each agent reaching its own store. It was also
three mechanisms deep by the end, because the CLI clients have no agent picker and needed the
same thing again in a different shape.

**What shipped instead is smaller: one ACTIVE team per person, stored, switched in ZZ Access.**
`teamsFor()` already returned `{active, all}` — the concept existed, and `active` was just
`every[0]` of an ORDER BY. It is now a column on `principal`, and `switch_team` moves it. That
deleted the header, the per-team agents, the per-team server entries, the generator that wrote
them, and `?team=` on the client package. One agent again, one server entry, one package.

A person in one team — nearly everyone, nearly always — meets none of this.

**Verified by hand on this host, 12/12**, with a second team and a person in both: `my_teams`
reports who they are acting for and every team they are in; switching moves the store and what
they can see; switching back moves it back; one team cannot see the other's documents; a team
they are not in and a team that does not exist are both refused, and neither moves them.

One real bug surfaced there and is worth recording, because reasoning would not have found it:
the switch worked but the store lagged. Team lookups were cached for a minute — harmless while
the team was derived and could not change, but a person switching would keep writing into the
team they had just left. Now three seconds, with the stale-on-error fallback intact.

Two things were kept deliberately. A bound token still outranks the active team: that is
automation confined to a team, and the point of binding is that it cannot wander. And a stored
team that is no longer a live membership is ignored rather than obeyed — removal has to
actually remove.

## Not verified

- **The five-scenario round has never been green. The best result is 3 of 5**, reached twice.
  S1, S3 and S4 pass and close their own initiatives, confirmed by name against the ledger.
  This release is therefore NOT proven against the flow it exists to run, and nothing below
  should be read as saying otherwise.

  Both remaining failures are one cause, and it is not the flow. S2 and S5 each hit a `422`
  from the case platform, saw only `Request failed with status code 422` — no field, no
  reason — concluded the platform was broken, and parked. Neither was right: running S5's own
  workflow with a valid payload reproduced its `400` and isolated it to a case type name it
  had transposed itself, `Consultation Afternoon (pilot-…)` against the `Afternoon
  Consultation` it had created. Same call, correct name, case created.

  The failure compounded: S5 cited S2's initiative as corroboration — "exactly the platform
  issue recorded in the consultation-booking initiative". **A wrong conclusion, written into
  the record, became a fact for the next agent.** Nothing in the document chain separates
  verified from concluded, and that is unfixed.

  What has been done about it: the peer error now names the operation and the arguments sent,
  and says not to assume the peer is down. What has not: the fixes for both failures — that,
  the waiver routing, and the stakeholder rewrite — have never been through a live round.
  They are changes made in response to a diagnosis, not changes shown to work.

- **The stakeholder that directs the conversation.** Built, and unexercised. The scripted
  answers are still there as a fallback, and `SMOKE_STAKEHOLDER=script` forces them.
- **A bundle install from published images.** `ghcr.io/zhixuan312/zz-stack:0.2.0` has not
  been pushed, so the install path a recipient actually takes — untar, `docker compose up
  -d` — has been exercised only from a source build.
- **Rollback to Open WebUI.** Not applicable on this host: it never had one. On a host
  being migrated, retaining the old container, volume and `public` tables keeps rollback a
  proxy change rather than a restore.
- **The deck.** Moved out of the tree to `docs/support/`, which is not tracked. It still
  carries a screenshot of the OLD front end and its build now refuses rather than embedding
  one silently, so retaking it is a prerequisite to showing it again — but it is no longer
  something a release can be wrong about.
- **Scenario routing without the `"By using ops-flow"` prefix.** The prefix was removed from
  every scenario, and the rounds since have routed correctly without it — so this is no
  longer unverified, but it was never the subject of a test of its own.
