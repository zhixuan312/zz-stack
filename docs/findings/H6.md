# H6 — a verdict looked up later is a verdict about the wrong day

FOUND while building the baseline table. Re-running `ladder-report.sh` against rounds 6 and 7
returned `not-accepted` for two rounds that were both read as `accepted` when they ran.

Nothing regressed. The report reads the team's LIVE ledger, and the store is emptied before
every round — so asking it about round 6 after round 8 asks about an empty store and gets the
only answer an empty store has.

This is the same shape as the block contamination, inverted. That one let a round see the
PREVIOUS round's state; this one lets a reading see a LATER round's state. Both come from
treating a shared mutable environment as if it held still.

WHY IT MATTERS MORE THAN IT LOOKS. Every claim in this log of the form "the round was accepted"
was true when made and unverifiable afterwards. A suite that recomputes verdicts from a live
store will, on its next full re-read, report every historical round as a failure — and the
reading will be indistinguishable from a real regression.

THE FIX: the verdict and the ledger row it came from are written into the round's own directory
at the moment the round ends, and never recomputed. `ladder-loop.sh` already did this and
manual rounds did not, which is exactly the gap: the careful path existed and the path actually
used bypassed it. Moved into `ladder-round.sh` so it happens whoever starts the round.

The rows above were restored from the ledger output quoted at the time each round finished.
